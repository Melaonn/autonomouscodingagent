# Using the harness from Codex

After the application owner has configured the installation-wide GitHub identity provider, start the service with `start.ps1` and select **Continue with GitHub**. Developers never register OAuth clients or paste personal access tokens. Browser consent verifies identity only and requests no repository, organization, or workflow scopes. The harness uses the existing checkout and local Git credentials for repository work and optional remote delivery. Then run `connect-codex.ps1` once and restart Codex so it loads the local `sdlc` server. Repository policy is created automatically from the first local checkout you use.

Open your existing checkout in the Codex app or CLI and enter native Plan mode. Give Codex the same high-level request you normally would. During planning, Codex calls `sdlc_start`. On first use, it auto-fills a capability inventory from local project metadata and asks about E2E applicability, CI, and optional deployment. After the answers, Codex calls `sdlc_start` with `confirmSetup=true` and a structured `setupDecision`. The returned bootstrap tasks become part of the native plan. After you accept that plan, the same conversation creates the missing scripts, configurations, meaningful test layers, CI, and explicitly requested deployment infrastructure. Future runs use one start call and reuse the verified policy.

After you accept the plan, Codex edits the same checkout. It proceeds directly to `sdlc_verify` unless a concrete implementation problem needs a focused command. The first verification traces every requested behavior and edge case to an exact quote, measurable acceptance criterion, and focused test evidence. Verification performs the configured setup, build, lint, type, unit, integration, E2E, secret, static-analysis, and dependency gates. Independent checks run concurrently where safe. When repository policy requires it, source changes must include a changed test path before verification can pass. Gate progress is written to the dashboard without repeatedly waking the model; failed gates return bounded diagnostics to the same conversation.

Verification evaluates the repository's review policy. An administrator can require review for every change or use an explicit risk policy based on the declared change risk, configured sensitive path globs, changed-file count, and acceptance criteria that require review evidence. The controller does not guess risk from prompt keywords. When review is required, type `/review` and choose **Review uncommitted changes**. Review must provide a verdict for every accepted criterion and independently account for every clause in the original request. Missing or unverified coverage sends the same conversation back to repair. Low-risk changes skip this extra model turn when policy permits.

A normal delivery uses `sdlc_start`, `sdlc_verify`, and `sdlc_publish`. Required review adds `sdlc_review`. Failed checks repeat only verification. GitHub CI, deployment, rollback, and health monitoring continue in the control plane without consuming Codex turns. Deployment approval remains a human action in the dashboard.

The MCP bridge cannot switch Codex modes or invoke slash commands. It does not clone the repository, launch a hidden coding agent, expose credentials, or approve deployment.
